# Helper module

The private `@ovs/helper` pnpm package owns the instance-scoped Bilibili Tampermonkey script, bounded media delivery, bridge JSON parser, and shared video codec allowlist.

Run these commands from the repository root:

```bash
pnpm --dir modules/helper run build
pnpm --dir modules/helper run test
```

The build reads `versions.helper` from root `versions.toml`. It writes `dist/helper.user.js` and `dist/release.json`.
The script includes the launcher, bridge parser, codec allowlist, release version, and a SHA-256 build fingerprint. The frontend checks the fingerprint during handshake, including when development changes keep the same release version. Origin and match placeholders remain for the server to scope at delivery.
The package exports `@ovs/helper/bridge-json`, `@ovs/helper/media-codecs`, and `@ovs/helper/release` for the frontend.
Generated metadata is not a second version source. The bridge protocol version remains separate from the release version.

On top-level `https://www.bilibili.com/video/` and `/bangumi/play/` pages, the helper adds a small **OVS** action to the video's action bar. Use Bilibili's neutral text, surface, and hover colors; show the site menu only after activation. A compact neutral floating fallback remains available until an action bar appears. Follow delayed rendering and action-bar replacement during in-page navigation, dismiss the menu on outside input or Escape, and keep it within the viewport. Helpers from different OVS instances share one menu and register distinct full origins. Selecting a site opens its `/import` page with only the current BV and part, episode ID, or season ID in the fragment. The launcher reads the current URL at activation, so Bilibili navigation within the page uses the selected video. The Bilibili branch never registers the privileged playback bridge or makes provider requests. Install the updated helper from each OVS instance to add its menu entry.

Candidate video previews use a read-only bridge operation. They return bounded metadata without taking playback ownership or creating a stream handle. Closing or rejecting a preview preserves the current player's requests and handle.

Selected-track metadata can include bounded numeric bitrate and frame rate. The browser-local `statistics` operation requires the active media handle and generation and returns only cumulative media response bytes and a monotonic sample timestamp. Count actual audio/video requests once, including observed progress before cancellation and repeated network transfers. Serving cached read-ahead bytes does not add another download. API, thumbnail, and danmaku requests do not enter this counter. Source addresses and platform credentials stay inside the helper.

Bangumi previews accept `seasonId` or `episodeId` with `part:1`. Resolve `/pgc/view/web/season` locally, selecting the first main episode for a season input. Return concrete BV/CID and `episodeId`. Opens and expiry refreshes retain that EP, validate its BV mapping, and use `/pgc/player/web/playurl`. Episode-list entries also carry their EP. Keep each participant's own session and reject platform denials and trial-only (`is_preview`) streams. PGC responses use the existing 1 MiB JSON bound and resolution deadline. Signed URLs and provider objects remain inside the helper.
Video metadata responses allow up to 4 MiB because Bilibili includes collection details. Collections above 500 episodes are omitted from the page without blocking the selected video. If the video metadata response exceeds 4 MiB, abort it and use `/x/player/pagelist` to resolve only the selected BV/part, without a collection list. This fallback retains the original resolution deadline and its own 1 MiB response bound. Other JSON responses retain the 1 MiB limit; media and thumbnail bounds remain separate. Access, network, and malformed-response errors do not trigger the fallback.

Progress-bar thumbnails use separate `thumbnails` and `thumbnail` operations bound to the current media handle. Use the image addresses, cell dimensions, and grid layout returned by Bilibili's videoshot API. Permit HTTPS image addresses in `hdslb.com` and its subdomains without hardcoding individual CDN hosts, paths, extensions, query parameters, or image resolutions. Image locations remain in helper memory; return opaque per-origin group IDs with the geometry. Run downloads independently per source origin, with two active requests per origin and no shared download cap or cross-source cancellation. The background producer uses the same per-origin grouping for its bridge replies and download workers, separately from foreground control replies. Transfer each sheet in chunks up to 256 KiB with a 4 MiB per-image response bound; release helper transfer bytes after the last chunk. Cache all completed compressed sheets in adapter memory and decode only the hovered cell. Video pumping and seeking do not gate independent CDN work. Retry transient metadata and image failures with capped backoff, retaining completed sheets and allowing other origins to continue. Cache updates refresh stationary previews. Replacement or disposal cancels owned work and releases cached images. Video loading and readiness never wait for thumbnails. Install the updated helper to enable Bilibili seek previews.
Previews and opens check exact MediaSource codec support. Select the requested playable quality or the highest playable quality, then prefer AV1, HEVC, and AVC in that order. Keep the selected video and audio representations when refreshing expired locations.

Preview and open resolve metadata through two sequential API requests, or three when the single-video fallback is needed, within a shared 24-second helper budget. Their frontend bridge allows 30 seconds. Each network request still has a 12-second maximum. Byte operations keep their separate 12-second total budget and 15-second bridge deadline.

`media-delivery.js` keeps signed locations, one current network window, and at most one following window in helper memory. Each window is at most 2 MiB. Download the following contiguous window while the page consumes the current window, without crossing the current fragment boundary. Align windows to 256 KiB page chunks so unused tails are not downloaded again. Network reads deliver page chunks of at most 256 KiB. Settle background failures and retry on demand within the byte operation's deadline. Cancel old windows and owned requests on seek, disposal, or location replacement. Retain up to three permitted provider locations, try mirrors on network failures, timeouts, HTTP 403/410, 404/408, or 5xx, and try unused mirrors on sustained insufficient delivery. Measure network duration without counting the time prefetched bytes wait for consumption. Verify initialization/index bytes before continuing on another source. Try each location at most once per byte operation, permit recovered sources in later operations, and exclude mismatched sources until expiry refresh. Cancellation, denied redirects, oversized responses, and HTTP 429 stop without trying another source. Retain a usable current source if alternatives fail validation. Mirror attempts and expiry refresh share a 12-second byte-operation deadline. Exact Content-Range validation rejects shifted or incomplete responses.

Timeouts halve the read-ahead cap down to 256 KiB while retaining at least the requested bytes. Keep the smaller cap across retries and location refresh. After two consecutive full network windows each complete within one quarter of their request timeout, double the cap toward 2 MiB. The frontend retries transient media network errors, timeouts, HTTP 408, and 5xx at the same cursor up to three times with 250, 500, and 1000 ms delays. Retain appended data during recovery and cancel obsolete retries on seek or disposal.

Byte requests can include a fragment `end`, byte `rate`, and `seek` generation. The nonblocking `seek` operation cancels obsolete media reads and refresh requests without cancelling unrelated API, thumbnail, or danmaku requests. Keep two active requests per source origin, with separate per-second bridge message bounds of 128 byte calls and 32 other calls. These message bounds protect local dispatch and do not combine source download capacity. The helper build fingerprint includes the delivery module; install the updated helper when OVS requests an update.

`make helper-build` also copies the distribution into `modules/sync/internal/helper/dist/` for Go embedding.
The server serves the script and release metadata under the existing `/userscripts/` routes.
Install the helper from the running OVS instance so its deployment origin is correct.
For frontend hot reload, `make dev-web` serves the generated files with the exact `localhost:5173` or `127.0.0.1:5173` origin. Install from that development page and reload.
